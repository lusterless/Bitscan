## What was checked

- **Superuser surface.** Everything runs inside `bootstrapped_server()`, before the `PgServer` is yielded and before any migration or test:
  1. the TS §5.2 Bootstrap, read from the spec at test time by heading and fence (`spec_sql.bootstrap`). That is 7 statements on `postgres`, then `\c bitscan` as a reconnect, then 5 on `bitscan`, executed as bytes, verbatim;
  2. three `ALTER ROLE {} PASSWORD {}` statements for the LOGIN roles, built with `sql.Identifier` and `sql.Literal`;
  3. the `bitscan_ref` database half: the 3 non-role statements with only `DATABASE bitscan ` renamed (an assertion fails if a statement is not renamed), then the same 5 on `bitscan_ref`.

  The spec DDL for #40 is then applied to `bitscan_ref` only, as `bitscan_migrate` with `SET ROLE bitscan_owner`. Never as superuser, never on `bitscan`, which matches the #40 ruling.

  tester-b's log run (CHK-M1-036-r1) found 0 superuser statements after the first app-role statement. The extra statements come only from the image entrypoint and the Testcontainers readiness probe.
- **No test can reach superuser credentials through the harness:**
  - `PgServer` holds only host, port, the port bindings and the three LOGIN-role passwords;
  - the container object is not kept;
  - `dsn()` and `connect()` refuse any role outside `LOGIN_ROLES`;
  - `_role_conn` asserts `session_user` and `rolsuper = false`.

  No test module other than `conftest.py` imports Docker or Testcontainers or names `postgres` as a role, except the two refusal tests.
- **Network and TLS:**
  - 5432 is published on `127.0.0.1` only, checked from both `HostConfig.PortBindings` and `NetworkSettings.Ports`;
  - `ssl=on`, and `pg_hba.conf` has only `hostssl … scram-sha-256` for TCP. The `local … trust` line is the container's Unix socket, used by the entrypoint and the probe;
  - every fixture connection is `sslmode=require`, and TLS use is checked on both client and server side (`pg_stat_ssl`);
  - `sslmode=disable` is refused with "no pg_hba.conf entry".
- **No committed secrets:**
  - passwords are `secrets.token_hex(16)` per server, for the superuser and each LOGIN role;
  - the TLS key is generated at image build time, not committed;
  - the image is pinned by the digest I verified in TASK-003.
- **Cleanup and hook:**
  - Testcontainers removes the containers, and `docker ps -a` is empty after every run (tester-b);
  - the image is kept by design (`clean_up=False`);
  - the skip/exit hook is covered by `test_conftest_hook.py` (pytester, CHK-M1-030).
- **Test quality:**
  - 17 mutations. Every committed-suite-visible one goes red: port defaults or `0.0.0.0`, `host` instead of `hostssl`, an extra `host` line, `ssl=off`, a superuser fixture, a reachable superuser password, an extra superuser `GRANT` or `CREATE TABLE`, and a spec edit adding `CREATEDB`;
  - the spec-extraction unit tests reject a wrong `\c` target, an extra meta-command, no reconnect, no heading and a missing semicolon;
  - locally, `test_pg_harness.py` and `test_conftest_hook.py` give 17 passed and 12 skipped (pg); in WSL, 295 passed.

## Rulings

1. **Observation 1: a superuser statement after the bootstrap, or an extra read-only one, stays green. I agree with main: make it a committed `pg` test before CHK-M1-240.** Requirements for that test:
   - It uses its own container started with `log_statement=all` and `log_connections=on`.
   - It asserts that the superuser statements equal the planned list (Bootstrap, three `ALTER ROLE`, `bitscan_ref`), plus an explicit allow-list for the entrypoint and probe statements, and that none comes after the first non-superuser connection.
   - The log needs the container. Have the harness capture the log text at teardown into a fixture value, and never expose the container or its environment.
   - Redact `PASSWORD '…'` literals before the text is stored or printed on failure.
2. **Observation 2: password randomness is not asserted. I agree: add the committed test before CHK-M1-240.** Assert that each LOGIN-role password is 32 hex characters, that they are pairwise distinct, and that they differ between `pg_server` and `fresh_pg_server`. That turns tester-b's FIXED_PASSWORD mutation red.
3. **Observation 3: Ryuk publishes its control port on `0.0.0.0` and `[::]`. Accepted as is.** It is the Testcontainers reaper's control port. It carries no credentials or data, and the worst a network peer could do is keep or reap this run's test containers. CI runners are ephemeral. Do not disable Ryuk, and keep the digest pin (TASK-009).

## Findings

1. **nit (tester-b observation 5).** Both testers' trees build the same tag `bitscan-test-postgres:16` on one Docker daemon, so concurrent runs can retag the image under each other. Suggest tagging by a hash of the `postgres/` build context (for example `bitscan-test-postgres:16-<sha256[:12]>`).
2. **nit.** "No test can reach superuser credentials" holds for what the harness hands out. A test could still bypass it on purpose: it could use the Docker SDK to read the container's `POSTGRES_PASSWORD`, or `docker exec` into the `local trust` socket. A one-line committed check would make this a gate rather than a review point: no `manager/tests/*.py` other than `conftest.py` imports `docker` or `testcontainers`.
3. **note (tester-b observation 4).** The spec's `GRANT USAGE ON SCHEMA public TO …` has no visible effect on PostgreSQL 16, because PUBLIC keeps `USAGE` on `public`. That is a grant-probe topic for TP-M1-10 / TASK-018, not a harness defect.

### Should-fix (statement-log test, `test_pg_harness.py:285-336`)

1. **Parameterised or prepared superuser statements are not seen.**
   - `_parse_log` matches only `LOG:  statement: `.
   - psycopg uses the simple protocol only when a query has no parameters (`psycopg/_cursor_base.py:448-459`). With parameters, or once auto-prepare starts, it uses the extended protocol. With `log_statement=all`, PostgreSQL logs that as `LOG:  execute <unnamed>: …` (or `execute _pg3_N: …`).
   - So a harness change such as `su.execute("SELECT %s", (1,))`, or any superuser query with a bound value, after the bootstrap would pass this test.
   - Fix: also collect `LOG:  execute ` lines, taking the text after the second `: `, and treat them like statements. Add a planted case: a parameterised superuser query after the first app connection must turn the test red.
2. **The allow-list matches by prefix.**
   - `s.startswith(("select version();", "SELECT 1 FROM pg_database WHERE datname"))` also exempts a simple-protocol string such as `select version(); GRANT … TO bitscan_app`, because a multi-statement query string is logged as one line.
   - Fix: compare each allowed statement for exact equality with its full logged text (the probe's `select version();` and the entrypoint's complete `pg_database` query), and require that each allow-listed statement comes before the first app connection.

### Nits

1. `test_image_tag_is_the_build_context_hash` re-implements `_context_tag`, so it shows the two copies agree, not that the tag changes with the context. Stronger: compute the tag over a temp copy of `postgres/` with one byte changed and assert it differs.
2. The import guard scans only the top level (`glob("*.py")`) and only static imports. Use `rglob` so future sub-packages are covered. `importlib` and `__import__` evasion stays with review.
