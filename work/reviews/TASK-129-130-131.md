## TASK-131: id-only cursors (4 files, +102 / −43)
REQ-143; TS §6.3 L1134, §6.2 L1108 and L1110, §5.2; #89; plan `work/plans/TASK-131.md`.
- **Spec and plan.** Order and page shapes are unchanged (#68).
  - The `/agents` cursor holds only the canonical lowercase hyphenated UUID string (`str(UUID(s)) == s`), so the 32-hex and `urn:` forms are refused, as builder checklist item 5 requires.
  - The package cursor holds only an int in 0 to 2^63 − 1, with booleans refused.
  - The anchors are read by fixed parameterised `SELECT`s inside the route's existing transaction (ruff S608 clean; plant 334 red).
  - A vanished anchor raises the existing `AnchorGone`, and the route answers 400 `invalid_request` with fixed text (checklist item 12), as `/packages/search` does.
  - No field was added to `AgentItem` or `AgentPackageItem`, and `openapi.json` is byte-identical (G6).
- **404 → 400 for a cursor naming a missing agent (lead point):** correct, as agreed with main. A cursor is a query value, and REQ-143 (3) and TS §6.3 ask for 400. Unknown path ids still get 404.
- **A signed `[package_id]` for a package that agent never had still anchors (tester point):** acceptable.
  - Only the server mints cursors (HMAC), and the scope `agent_packages:{agent_id}` binds each cursor to one agent's list.
  - Anchoring on `package` rather than `agent_package` is the plan's deliberate choice, so paging continues after an inventory change.
  - The worst case is a page that starts after a sort key, and that key is any package name. Nothing leaks: the anchor's values are never returned.
- **Layering.** `api → services → repositories` is kept. `AnchorGone` passes through the service, and the route maps it to 400.
- **Tests.** The tester's suite has 45 tests on PostgreSQL: boundaries with 255-character non-ASCII values, the tie-break, `1.0` / `1.0-0`, the cursor length, and 26 malformed payloads. The plants turn it red against a 74/74 control.
